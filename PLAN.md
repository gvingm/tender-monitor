Риски стека:
- **Всё завязано на Lark** — единая точка отказа (Bitable + чат). Альтернативы в §6.

## 6. Скачивание файлов тендера (основное требование)

**Ответственный scope:** `GET /api/tenders/attachments?id=<_id>` — возвращает массив всех файлов тендера `{displayName, href, realName, size, publicationDateTime}`.

Пайплайн (реализован в `main.go`, `processFileDownloads`):
1. Опрос Bitable каждые 5 мин (+ ручной `POST /files/run`): записи `Статус="На рассмотрении"` AND `ФайлыЗагружены=false`.
2. По `TenderplanID` → `/api/tenders/attachments` → список файлов.
3. Скачивание каждого `href` потоково во временный файл (таймаут 60с/файл); при 401/403/404 — прокси `/api/tenders/file?href=`.
4. Загрузка в карточку: `drive/v1/medias/upload_all` (parent_type=`bitable_file`) → один `PUT` записи со всеми file_token в поле «Файлы» → `ФайлыЗагружены=true`.

## 7. Lark как интерфейс-канбан: оценка и альтернативы

### Подходит ли Lark? — **Да, при текущем контексте это оптимальный выбор**

Аргументы «за»:
- Уже работает: валидные ключи, созданная Bitable «Тендеры Дидал-СК», чат с уведомлениями, сотрудники уже в Lark.
- Bitable имеет **канбан-представление** по полю «Статус» (Новый → На рассмотрении → ...) — перетаскивание карточек понятно непрограммистам.
- **Поле-вложение** («Файлы») нативно хранит документы в карточке — именно то, что требуется; файлы доступны из мобильного приложения Lark.
- API покрывает всё: search по статусу, upload медиа, обновление записей.
- Бесплатного тарифа Lark достаточно для такого объёма.

Ограничения:
- Нет нативного webhook «статус изменился» из Bitable Automation в бесплатном тарифе во всех регионах → используем опрос каждые 5 мин (приемлемо; «максимально быстро» = до 5 мин задержки, при желании — `POST /files/run` вручную для мгновенного запуска).
- Лимит размера вложений Bitable (до ~1 ГБ на файл через media upload) — для тендерной документации достаточно.

### Альтернативы (если Lark по какой-то причине отпадёт)

| Инструмент | Канбан | Файлы в карточке | API/webhook на смену статуса | Цена | Простота для «простых людей» |
|---|---|---|---|---|---|
| **Lark Bitable** (текущий) | ✅ | ✅ до ~1 ГБ | опрос/автоматизация | бесплатно | высокая, уже внедрён |
| Notion | ✅ | ✅ до 5 МБ (бесплатный план — критично!) | ✅ webhook | бесплатно*, но лимит файлов убивает сценарий | высокая |
| Trello | ✅ | ✅ 10 МБ/файл (free) | ✅ webhook нативно | бесплатно*, лимит файлов критичен | очень высокая |
| Wekan (self-hosted) | ✅ | ✅ без жёстких лимитов (свой сервер) | ✅ REST API + исходящие webhook | бесплатно (self-host) | средняя, нужно хостить |
| Plane (self-hosted) | ✅ | ✅ | ✅ webhook | бесплатно (self-host) | средняя, заточен под разработчиков |

**Вывод:** остаёмся на Lark. Notion/Trello упираются в лимиты размера файлов на бесплатных планах (5–10 МБ — тендерная документация часто больше). Self-hosted альтернативы (Wekan/Plane) требуют отдельного сопровождения и не дают преимуществ перед уже внедрённым Lark. Единственное улучшение, которое стоит рассмотреть позже: Lark Base Automation (триггер «запись обновлена» → HTTP-запрос на наш `/files/run`) уберёт 5-минутную задержку, если доступна на тарифе.

### Публичный доступ (через Tailscale Funnel)
- Порт сервиса опубликован в swarm в режиме `host`: `8787->8787` (ingress-режим не работает с rootless docker).
- WSL localhostForwarding пробрасывает его на Windows `127.0.0.1:8787`.
- Funnel: `tailscale funnel --bg --https=8443 http://127.0.0.1:8787`.
- **Публичный URL: https://desktop-83vpv0v.taild661d0.ts.net:8443/** — проверен извне (HTTP 200, `{"status":"ok"}`).
- Webhook для Mail Assistant: `https://desktop-83vpv0v.taild661d0.ts.net:8443/webhook/mail-tenders`.
- Камеры на порту 80 не затронуты, пробросы на роутере не менялись.
- Домен `dokploy.albion1.ru`: Funnel не поддерживает custom-домены (только `*.ts.net`). Вариант — HTTP-редирект с `dokploy.albion1.ru` (хостится на Vercel) на URL выше.
- Внимание: Funnel-прокси не должен указывать на WSL-IP напрямую (172.31.x.x) — tailscaled на Windows его не достаёт, только `127.0.0.1`.
